## What changed since 2026-05-25

**Missing AST node classes: 17 → 0.** The previous scan listed 17 Missing classes
(218 nodes total, 2.71% of the tree). The current scan finds zero — every node
class Sinatra's `lib/` reaches for is now in the rubyrs subset. Supported share
moved 82.46% → **85.17%** (+2.71pp); RidesAlong is unchanged at 14.83%.

The 17 classes that closed since the previous scan, in descending count:
`BlockParameterNode` (×58), `RestParameterNode` (×44), `RegularExpressionNode`
(×39), `AliasMethodNode` (×16), `KeywordHashNode` (×12), `ConstantWriteNode`
(×10), `AssocSplatNode` (×6), `DefinedNode` (×5), `GlobalVariableReadNode` (×5),
`KeywordRestParameterNode` (×5), `NumberedReferenceReadNode` (×5),
`ClassVariableReadNode` (×4), `SingletonClassNode` (×3),
`ClassVariableWriteNode` (×2), `InterpolatedRegularExpressionNode` (×2),
`BackReferenceReadNode` (×1), `LambdaNode` (×1).

The downstream effect shows up in per-file translatability: **all 5
non-trivial files (≥20 nodes) are now 100%**, where the previous scan had 1
file at 100% and 4 at 95–98%. That includes `sinatra/base.rb` (7113 nodes,
previously 97.48%), the file the spike work was structurally blocked on.

What this **does not** say: it doesn't say Sinatra runs. AST-level supportedness
is an upper bound — runtime gaps (built-in methods, `require` chain,
encoding, Rack, etc.) still apply. See
[TRY_RUNS.md](TRY_RUNS.md) for the empirical runtime picture; on this same
2026-05-26, `sinatra/base.rb` parses to completion at runtime too, but the
first executable statement is `require 'rack'` — the file moves from "AST
blocks parse" (Cat D) to "C-ext require wall" (Cat B), which is two
categories up but still not Cat A.
