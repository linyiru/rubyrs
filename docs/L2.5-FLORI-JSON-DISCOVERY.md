# Level 2.5 discovery: flori/json drop-in audit

Status: **superseded** by L3 spike landings. The original audit (below,
from L2.5) concluded unchanged drop-in was unreachable without
architectural work; both pieces of that architectural work have
since landed and **parser-side drop-in actually works today**. The
body is preserved as historical record — read the status update
first; treat the original "TL;DR" / "Recommended paths forward"
sections as the planning input they were, not as current state.

### What works today (unmodified flori/json source)

`crates/rubyrs/examples/flori-json-cext/vendor/{parser,generator}/`
holds the unmodified flori/json 2.9.1 sources. `build.sh` compiles
both into `parser.bundle` + `generator.bundle` against the
`rubyrs-cext` header shims. Manual run on 2026-05-26:

```ruby
require '.../flori-json-cext/parser'
JSON::Ext::Parser.new(
  '{"name":"rubyrs","ver":4.7,"tags":["ruby","rust"],"ok":true,"nil":null}'
).parse
# => {"name" => "rubyrs", "ver" => 4.7, "tags" => ["ruby", "rust"],
#     "ok" => true, "nil" => nil}
```

End-to-end working pieces (proves the L3-A/B/F/H spikes were real,
not just unit-tested):

- TypedData wrap path constructs `JSON::Ext::Parser` instances
  (parser state IS a `JSON_Parser` C struct, allocated via the
  registered alloc func, freed on GC via the TypedData dfree
  callback)
- Parser state survives across cross-call boundaries (Ruby
  `parser_obj.parse` → C `cParser_parse` → C `parse_value` recursion
  → returns hashes/arrays/strings/numbers/bools/nil back to Ruby)
- `rb_raise` from inside parser.c on malformed input lands in a
  Ruby `rescue => e` clause:

  ```ruby
  begin
    JSON::Ext::Parser.new('{bad').parse
  rescue => e
    # e.class    => RuntimeError
    # e.message  => "unexpected token at '%s'"  (see caveat below)
  end
  ```

### What does NOT work yet

1. **Generator leg of flori/json** — `JSON::Ext::Generator::State.new`
   instantiates, but calling `state.generate(obj)` raises
   `NoMethodError: undefined method 'generate' for Object`. Cause:
   the flori/json gem ships `lib/json/ext/generator/state.rb` (pure
   Ruby) which injects the user-facing methods onto the C-defined
   State class; rubyrs's `require` lenient pass-through stub
   no-ops that file (`rb_require: ignoring json/ext/generator/state`
   in stderr). To close: either (a) actually load that Ruby file
   through `require`, or (b) move those methods into the C side.
2. **`rb_sprintf` format expansion** — the raise message above comes
   through with the literal `%s` unsubstituted. The raise mechanism
   works; only the formatter is incomplete. Cosmetic for now; matters
   when error messages need to carry the offending token.
3. **No regression test for flori-json** — `crates/rubyrs/tests/`
   has `cext_mini_json.rs` and 7 `cext_msgpack*.rs` files but no
   `cext_flori_json.rs`. The parser path that works today is not
   pinned in CI; a regression would go unnoticed.

### Recommended next moves (in priority order)

1. Add `crates/rubyrs/tests/cext_flori_json.rs` that locks in the
   parser path — at minimum a round-trip on a non-trivial fixture
   plus a `rb_raise` propagation assertion. Single commit, prevents
   silent regression.
2. Close the generator leg. The cheaper fix is probably (b) — port
   the small `state.rb` helper into `generator.c` — because option
   (a) drags in the wider question of how rubyrs resolves Ruby
   files shipped inside a gem's `lib/`, which is broader than this
   spike.
3. Implement enough `rb_sprintf` to substitute `%s` / `%d` /
   `%"PRIsVALUE"`. Doesn't unblock anything new but makes error
   messages from the existing parser usable.

Once (1) + (2) ship, the doc title should change from "discovery"
to "completed spike" and this file can move into the historical
record proper.

## Original audit (L2.5, preserved as historical record)

> The TL;DR and recommendations below describe the situation
> **before** the L3 work landed. They were accurate when written
> and informed the spike sequence that closed the gap; current
> state is the section above.

## TL;DR

**Unchanged-source drop-in is NOT achievable at Level 2.5.** Two
Level-3-class architectural blockers stand in the way: `rb_raise` /
`longjmp`-style exception propagation, and `rb_data_type_t` / RData
(C struct wrapped as Ruby object with mark function). Both are
pervasive in flori/json's parser.c (the parser state IS RData; every
parse error is `rb_raise`).

Recommendation: defer unchanged drop-in until those land. Meanwhile,
two productive intermediate paths:

1. **"json-rs" subset** — write a C extension that implements the
   `JSON.parse` / `JSON.generate` Ruby API using only the cext ABI
   surface we currently expose. Bounded scope, fast to ship, real
   user value.
2. **Pick a smaller json-adjacent target first** — `oj` is similar
   shape but smaller; `json-pure` is pure Ruby (no cext needed,
   trivially works); `yajl-ruby` uses different patterns.

## Methodology

Pulled the actual flori/json source from the public repo:

```
gh api repos/flori/json/contents/ext/json/ext/parser/parser.c    → 56,334 bytes
gh api repos/flori/json/contents/ext/json/ext/generator/generator.c → 65,987 bytes
```

Enumerated every `rb_*` call, every `R*` / `Q*` / `NUM2*` macro, and
every `#include` directive. Cross-referenced against the rubyrs-cext
ABI surface as of L2-3 (`feat/cext-level2-collections` branch).

### 🟢 Trivial macro stubs (14 — most are no-ops or thin libc wraps)

These can land in a single afternoon: pure header additions, no
runtime cost:

- `Qundef` — sentinel handle (give it index 4 alongside Qnil/Qtrue/Qfalse/Object)
- `RTEST(v)` — `((v) != Qnil && (v) != Qfalse)` macro
- `RB_TYPE_P(v, T)`, `RB_SYMBOL_P(v)` — type check macros (need value-type-tag access)
- `RHASH_SIZE(h)` — mirror of `RARRAY_LEN` for Hash
- `rb_isalpha`, `rb_isdigit`, `rb_tolower` — `static inline` wrapping libc ctype
- `RB_LIKELY` / `RB_UNLIKELY` — `__builtin_expect` macros (or no-op `#define`s)
- `RUBY_DEFAULT_FREE` — constant pointer used as default free fn
- `RB_OBJ_FREEZE`, `RB_OBJ_WRITTEN`, `RB_ENCODING_GET` — runtime no-ops in spike (rubyrs doesn't model frozenness / write barriers / per-string encoding tags)
- `RVALUE_STACK_*` — internal stack constants flori/json's parser uses for SIMD-aware buffer management; can be `#define`d to safe defaults
- `rb_check_arity` — `static inline` runtime check

### 🟡 Small additions (~30 — functions, no architectural change)

Each is mechanical work in `rubyrs-cext` + a host-side translation
or no-op. Estimate: 3-5 functions per session, so 6-10 sessions
total for all of these.

**Array / Hash extras** (we have the foundation, just need more methods):

- `rb_hash_new_capa(long)`
- `rb_hash_bulk_insert(long, VALUE *kv, VALUE h)`

**String extras** (CRuby's String surface is wider than we expose):

- `rb_str_buf_new`, `rb_str_buf_cat`, `rb_str_set_len`, `rb_str_substr`

**Number conversions**:

**Object introspection**:

- `rb_respond_to(v, id)`, `rb_inspect(v)`

**Class / module definition**:

- `rb_require` — already we just need name resolution

### 🔴 Real architectural work (~24 — Level 3-class additions)

Each of these is "a new spike" rather than "an afternoon":

**Exception propagation from C** (THE blocker for parser.c):
- `rb_raise(VALUE exc_class, const char *fmt, ...)` — raise from inside C
- `rb_rescue`, `rb_ensure` — exception-aware control flow
- `rb_exc_new_str`, `rb_exc_raise` — programmatic exception creation
- `rb_check_frozen(v)` — raises FrozenError

Why hard: requires `setjmp` / `longjmp` (or equivalent) wiring inside
cext_dispatch so a C-side `rb_raise` unwinds through C frames back
to Rust, where it's converted to a `Trap`. Coordination between C
unwind and Rust's `Drop` invariants is delicate. Mirror work to
ADR 0009's "forward path" — see that ADR for the high-level design
sketch.

**Exception class handles** (need exported `VALUE`):
- `rb_eArgError`, `rb_eTypeError`, `rb_eRangeError`, etc.
- `rb_mKernel` — Kernel module

These can be `#[used] static`s exported from rubyrs, but they're
**only useful in conjunction with `rb_raise`** — flori/json uses them
exclusively as the `exc_class` arg to `rb_raise`.

**Built-in class handles**:
- `rb_cArray`, `rb_cHash`, `rb_cString`, `rb_cFloat`

Needed for `rb_obj_class(v) == rb_cArray`-style type checks throughout
generator.c. Smaller architectural lift — re-export the existing
rubyrs class objects as `extern VALUE` at known handles.

**RData / typed-data wrapped C structs** (THE blocker for parser.c):
- `rb_data_type_t` — descriptor for a C struct wrapped as Ruby object
- `RTYPEDDATA_DATA(v)` — extract C struct pointer
- `RUBY_TYPED_*` flags (FREE_IMMEDIATELY, WB_PROTECTED, EMBEDDABLE, FROZEN_SHAREABLE)
- `rb_define_alloc_func(klass, alloc_fn)` — register C allocator
- `rb_gc_mark`, `rb_gc_mark_movable`, `rb_gc_location` — mark function primitives

Why hard: requires `HeapObj` to grow a new variant `Custom {
struct_ptr: *mut c_void, mark_fn: ..., free_fn: ... }`, GC mark phase
to call the C mark fn, GC sweep to call free fn. Cross-FFI mark
function callbacks are the same UB-aliasing concern as L2-2's
`rb_funcallv` but worse (mark fn runs DURING GC, while heap is
being walked). Probably 1-2 weeks of solo work.

**Encoding subsystem**:
- `rb_utf8_encoding`, `rb_utf8_encindex`, `rb_ascii8bit_encindex`, `rb_usascii_encindex`
- `rb_enc_associate_index`, `rb_enc_interned_str`, `rb_enc_str_coderange`, `rb_enc_sprintf`
- `rb_utf8_str_new`

Why hard: every Ruby `String` in CRuby has an encoding tag. rubyrs
treats strings as `Rc<str>` (UTF-8) with no per-instance encoding
metadata. Adding the encoding subsystem is non-trivial value layout
work.

**Ruby-style format strings**:
- `rb_sprintf`, `rb_vsprintf` — like sprintf but returns Ruby String
- `rb_str_catf` — append formatted

Why hard: needs to parse `%`-format specifiers including `%"VALUE"`-style
for `VALUE` args (CRuby uses this for `inspect` chains in error messages).
Doable but requires a mini-printf clone.

**Misc Vm-level additions**:
- `rb_class_new_instance(argc, argv, klass)` — equivalent to `Class.new(args)`
- `rb_convert_type(val, type, name, method)` — `Object#to_*` coercion

## Strategic implication

**flori/json (the gem we'd target for "JSON support") cannot drop in
unchanged at any point on the current trajectory without committing
to `rb_raise` + RData**. Even with all the 🟢 + 🟡 items done (~50
hours of mechanical work), the parser would still fail at:

```c
static const rb_data_type_t JSON_Parser_type = {
    "JSON/Parser",
    {JSON_mark, JSON_free, JSON_memsize,},
    ...
};

VALUE JSON_Parser_alloc(VALUE klass) {
    JSON_Parser *json = ZALLOC(JSON_Parser);
    return TypedData_Make_Struct(klass, JSON_Parser, &JSON_Parser_type, json);
}
```

— the entire allocation path is RData-shaped. There is no work-around
at the rubyrs API surface; the architecture itself must grow.

## Recommended paths forward

### Path A: "json-rs" subset (1-2 sessions, ships now)

Write a fresh C extension `examples/json-rs/` that:
- Provides `JSON.parse(str)` and `JSON.generate(obj)` Ruby methods
- Uses ONLY the existing rubyrs-cext ABI surface (no RData, no
  rb_raise — just the L0..L2-3 surface we have)
- Parser state lives in a stack-allocated C struct passed by pointer
  through static recursion (no Ruby-object wrapping)
- Errors return a designated "error sentinel" Hash like
  `{"_error" => "msg"}` instead of raising
- Test vectors: a subset of the official JSON spec
  (https://github.com/nst/JSONTestSuite) we can pass

This proves "you can write a JSON gem on top of rubyrs's cext API
TODAY" — a real, useful intermediate milestone. Doesn't claim to be
a drop-in for flori/json; positions as "json-rs: a JSON gem designed
for rubyrs's cext surface".

### Path B: Pick a smaller gem first (1 session)

Survey targets that are JSON-adjacent but smaller in scope:
- `oj` — large (similar to flori/json)
- `multi_json` — pure Ruby wrapper, no cext
- `yajl-ruby` — different architecture (streaming SAX-style)
- `msgpack` — uses RData heavily, similar blockers
- `protobuf` — RData + lots of state, worse

`yajl-ruby` is interesting because its SAX-style API maps well to
the rb_funcall callback machinery from L2-2. But it still uses RData
for the parser state.

Hard to find a meaningful gem in the 100-1000 line range that doesn't
need RData. The bcrypt-shape (L1.5) was the sweet spot.

### Path C: Commit to Level 3 (the architectural work)

If the strategic goal is "host real flori/json", commit to the
~3 weeks of focused work to add:
1. `rb_raise` + setjmp coordination with Trap
2. RData + custom heap variant
3. Encoding subsystem (or stub)
4. The ~30 small additions (mechanical)

Output would be the first non-CRuby Ruby implementation able to host
flori/json unchanged. **This is the genuine "Level 3 — RData" spike**
sketched in the L0 ladder.

## Concrete next-spike candidate

If we want **information-rich** vs **value-delivering**:

- Information-rich: Pick `rb_raise` and prototype just IT. Single
  spike, ~1 week. Outcome tells us whether the exception propagation
  design works mechanically before committing the surrounding RData
  work.

- Value-delivering: Path A (`json-rs` subset). Ships a real working
  JSON gem in a couple of sessions, demonstrates the breadth of
  current ABI, sets up real benchmark vs CRuby+json on parse/generate
  workloads.

My recommendation: **Path A first** — it banks a real demonstrable
artifact ("rubyrs has a json gem") and surfaces any remaining ABI
gaps in real use. Then Path C (rb_raise spike) informed by what
json-rs taught us.
